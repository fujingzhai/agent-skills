# YouTube 音频文稿整理

从一条 YouTube 链接，产出一篇可读的文稿，落成普通 DOCX 文件。

## 全流程

```
⓿ yt check            检查依赖（yt-dlp 等），缺什么先装什么
① yt doc <url>        下最优字幕并洗成文稿（脚本干，快）
⓪ 找现成文稿          有没有人已经整理好了？见"⓪ 先找现成文稿"
② 通读校错            识别专名误识与说话人，见"判错指南"
③ 翻译（仅非中文）     你干，不调 API —— 见"翻译硬规矩"
④ 成稿组织            写摘要、分小节、标高亮
⑤ 导出 DOCX           用 scripts/to_docx.py 把 markdown 转成 docx
⑥ yt rm <video_id>    清临时文件
```

⓪ 编号在 ① 后面不是笔误：**先跑 `yt doc`**，它顺手把描述栏里的文稿链接挖出来给你，
再据此决定要不要找、值不值得找。反过来先搜是浪费。

⓪②③④ 是判断活，脚本不碰。⓿①⑤⑥ 是确定性的。

> 本文件中的 `yt` 指套件统一入口 `<套件目录>/yt`。若你不在套件目录内，
> 用 `python3 <套件目录>/yt <子命令>` 调用；`<套件目录>` 从本文件所在位置向上两级。

---

## ⓿ 依赖检查

```bash
yt check
```

输出会列出 Python、yt-dlp 可执行文件、yt_dlp Python 库、临时区与成稿目录的状态。
缺什么按它给的命令安装，装完重跑确认。**不要跳过这一步直接下载。**

## ① 下字幕并清洗

```bash
yt doc "<视频URL>"
```

输出会告诉你四件事：**选用了哪条轨**、**需不需要翻译**、**文稿在哪**、**工作区在哪**。

选轨优先级（脚本已实现，理解即可）：

1. 人工字幕·中文 → 最理想，直接可用
2. 人工字幕·视频原语言 → 质量最高的外语来源
3. 人工字幕·其它语言
4. 自动字幕·**仅原生语言轨** → 兜底

> **为什么绝不用 YouTube 的自动翻译字幕**
> `automatic_captions` 里除原生轨外的几百种语言，全是 YouTube 拿原生轨机翻的结果，
> 等于在语音识别误差上再叠一层翻译误差。用户看到的"[music] 被当成句子成分翻进正文"就是这么来的。
> 脚本只取原生轨，翻译交给你——你至少能看见上下文。

拿不到任何字幕时脚本会明确报错（该视频只能靠本地转录，本子技能暂不支持）。

## ⓪ 先找现成文稿

YouTube 的字幕不是唯一底本。**访谈、播客、大会演讲**这类内容，作者自己往往在官网发过整理稿，
质量高出自动字幕一整个档次——专名拼写正确、说话人有名有姓、分好了章节。
有这种稿子就该拿它当底本，而不是硬啃 ASR。

但这一步**有成本**，所以先看值不值得找。

### 值不值得找

| 情形 | 怎么办 |
|---|---|
| `yt doc` 打出了"现成文稿"候选 | **必查**。链接已经在手上，零检索成本 |
| 无候选 + 选用轨是**自动字幕** + 内容是访谈/播客/演讲 | 值得找，**检索预算 ≤3 次**，找不到就走字幕 |
| 无候选 + 已有**人工字幕** | 一般不必找。人工字幕本身够干净，唯一短板是**说话人身份**——多人对话且分不清谁是谁时，值得花 1 次检索去要个说话人标注 |
| 教程、vlog、新闻剪辑、音乐、中文频道 | 直接跳过。这类基本没有现成稿，别浪费调用 |

### 怎么找（按成本从低到高，命中就停）

1. **描述栏** —— 命中率最高的一条路。脚本已自动扫，结果在 `meta.json` 的
   `transcript_candidates`，也直接打在 `yt doc` 输出里。实测 Lex Fridman、Dwarkesh、
   Lenny's 都在描述里明写 `Transcript: <url>`。
2. **频道官网**（`meta.json` 的 `channel_url`，或描述栏里的自有域名）。已知规律：
   - Substack 系播客（dwarkesh.com、latent.space、lennysnewsletter.com）文章页多半带全文
   - `lexfridman.com/<嘉宾名>-transcript`
   - TED → ted.com 官方交互文稿（且有人工中译）
   - 公司大会 keynote → 官方博客常发"remarks"（注意这多半是 B 档，见下）
3. **付费墙的绕行**：正文付费不等于没有。Lenny's 官网文章付费，描述栏却另给了一个公开
   Dropbox「Transcripts Archive [public]」，按嘉宾名存 txt，全站免费。
   **付费墙不要翻，去找作者自己放出来的公开副本。**
4. **兜底检索**：从字幕里挑一句 8–15 词的独特句子，**加引号**搜。搜得到，说明有站点收了这篇。

### 四档判定 —— 这一步不能省

拿到一份稿子，先定它是哪一档，**档次决定用法**：

| 档 | 是什么 | 怎么用 |
|---|---|---|
| **A 逐字人工稿** | 带说话人名、时间戳，与字幕逐句对得上（lexfridman.com、dwarkesh.com） | **取代字幕当底本** |
| **B 编辑稿** | 明说"condensed and edited"、改写成文章体、官方博客的 keynote remarks | **只作校对参照**，正文引述仍用字幕 |
| **C 第三方 ASR** | HappyScribe、podscripts、transcript.lol、tubetranscribe、各种"YouTube 转文字"站 | **与自动字幕同级，不是权威**。它做了说话人分离才有边际价值，且必须对着字幕核 |
| **D 付费墙/残缺** | 只放前几段、要登录 | 不用 |

> **B 档为什么不能当原话引述**
> 英文引述块的唯一作用是让读者核对**原话**。a16z 的文稿页自己写着"condensed and edited
> for readability"，Google 的 I/O keynote 文稿是"adapted to include more of what was
> announced"——都不是他说过的话。拿这种稿子填引述块，性质等同于 AI 重写，
> 与下面"英文引述块 = 逐字照录"那条死规矩直接冲突。
>
> C 档同理：第三方站多数就是把 YouTube 自动字幕换个皮重发，甚至更差（丢时间戳、Whisper 漏句），
> 换过去等于白忙。

### 用之前必验三件事

- **覆盖全不全**：文稿词数 ≥ 字幕词数的 90%。低于这个数，多半是节选或被付费墙截断了
- **是不是同一版本**：播客音频版与 YouTube 版剪辑可能不同（广告段、片头、加长片段）。
  抽查中段和结尾各一句，对得上才算同一版
- **有没有时间戳**：没有的话，正文时间戳仍以字幕为准，文稿只用来正专名、分说话人

```bash
# 字幕词数（拿它当分母）
grep -o '[A-Za-z][A-Za-z-]*' transcript.txt | wc -l
```

验完在**元信息块的底本说明**里写清用的是哪一档、哪个来源。

## ② 判错指南

`transcript.txt` 每段以 `[HH:MM:SS]` 时间戳开头。**A 档现成文稿**当底本时本节基本可跳过
（作者已经校过），只需核对说话人切分；**人工字幕**一般干净，扫一遍即可；
**自动字幕**必须逐段核对——语音识别对普通词句相当准，但专名错得最狠，而且**错得通顺、不会引起怀疑**。

### 四类错误，分别处理

**第一类：专名误识（最常见，危害最大）**

实际踩到过的：

| 识别成 | 实际是 | 怎么发现的 |
|---|---|---|
| Lisa Doll | Lee Sedol（李世乭） | 讲围棋的视频里冒出没听过的女性名字 |
| Opening Eye | OpenAI | 读音接近，但语境里只可能是公司名 |
| AlphaChepan | AlphaChip | 前后都在讲 Alpha 系列，这个拼不出来 |
| gnome | GNoME | 讲材料科学时冒出"地精" |
| VO | Veo | 与 Nano Banana、Gemini 并列，只能是产品名 |
| The Big Orange Spot | The Big Orange Splot | 童书名，查得到正确拼写 |

**判据**：凡人名、产品名、公司名、机构名、论文/书名，一律停下来问一句"这个东西真的存在吗、在这个语境里说得通吗"。
说得通就放过，说不通就查。**不确定的必须标存疑，不许猜一个填进去。**

**第二类：同音词错误**
`in silicon` ← `in silico`、`fair play` 之类。看语境，技术语境里的怪词优先怀疑。

**第三类：说话人错乱**
YouTube 自动字幕**不做说话人分离**，`>>` 标记稀疏且位置不可靠；人工字幕多用 `-` 标换人，
知道"这里换人了"但不知道换成了谁。访谈类内容两人的话会大段糊在一起，
必须靠语义切：谁在提问、谁在回答、谁在自述经历。

> 这正是 ⓪ 最大的收益点：第一方文稿通常直接标了说话人姓名，
> 拿它对一遍比自己猜准得多。**哪怕字幕是人工的，为了说话人身份也值得去找一次。**

**第四类：多人交叉说话导致的崩溃**
现场录像、抢话片段，ASR 会彻底乱掉。**不要硬编成通顺句子**——
做成独立引述块，注明"以上为语义重构"，让读者知道这段不可靠。

### 说话人自己说错的，不算错误

例：讲疟疾时说 `malaria virus`（疟疾由寄生虫引起，非病毒）。这是**受访者口误**，
不是识别错误。**保留原文**，加备注说明，不要替他改。

## ③ 翻译硬规矩（仅当 `需翻译 = 是`）

中文字幕跳过本步，直接进 ④。

### 排版

中文正文在前，英文原文跟在后面用引述块 `>`：

```markdown
[00:21:26] **说话人**：中文译文。

> English original, verbatim.
```

### ⚠️ 英文引述块 = 逐字照录，这是死规矩

**英文引述块的唯一作用是让读者核对原话。它必须是原始字幕的逐字内容。**

**只允许**这三种改动：

- 删掉 `uh` / `um` / `like` 这类纯填充词
- 合并 ASR 打散的重复（`the the the` → `the`）
- 补标点和大小写

**严禁**：删句、改写、压缩、合并要点、"提炼精华"。

> **踩过的坑（2026-08-10）**
> 有 agent 把每段英文压到原来的 1/4（14092 词 → 3233 词），读者以为那是原话，实际是 AI 重写的——
> **比不放英文更糟，因为它有欺骗性**。
> 更严重的是丢了语义：原话 `There are no roles anymore. We haven't seen that.`
> 被压成 `There's been a lot written about role collapse.`，
> 说话人对"岗位消失论"的**否认**没了，中文顺势写成"我们确实看到了……"，**把反驳变成了认同**。

**自检（写入前必做）**：成稿英文引述块的总词数，应达到**底本**词数的 **85% 以上**。
底本是字幕就对字幕数，是 A 档现成文稿就对那份文稿数。低于这个数，
说明你在做摘要而不是文稿，回去重做。

```bash
# 原始词数
grep -o '[A-Za-z][A-Za-z-]*' transcript.txt | wc -l
```

B/C 档文稿**不进引述块**——引述块只放底本原文。

### 中文译文：中度清理

去掉 uh/um 和重复词、补全被打散的句子；**保留说话人的语气和口语节奏**。
目标是"一篇整理过的访谈"，不是"一篇重写过的文章"。中文同样不许漏译整句。

### 专名标注：备注只用来标不确定，不用来留痕

**能百分百确定的识别错误，直接改正，不要加备注。**

`Opening Eye` → OpenAI、`AlphaChepan` → AlphaChip、`Lisa Doll` → 李世乭，
这类改动没有任何判断风险，加备注只是在向读者汇报你的工作过程。
读者要的是一篇能读的文稿，不是一份校对日志——**每个备注都是一次打断，得省着用**。

| 情形 | 怎么做 |
|---|---|
| 百分百确定的识别错误 | **直接改，不加备注** |
| 拿不准的 | 标红 + 备注写明存疑理由，**不替用户下判断** |
| 受访者口误（非识别错误） | 保留原文 + 备注说明（因为没改动，读者会疑惑） |
| 人物、机构的背景补充 | 可用备注，但**克制**；重要信息直接写进元信息块 |

写法（DOCX 转换脚本认识以下写法，会转成对应格式）：

```markdown
存疑内容<sup>（说明为什么存疑）</sup>
```
```html
<span style="color: #d23f31;">存疑内容</span>
```

- `<sup>（说明）</sup>` → Word 上标小字
- `<span style="color: #d23f31;">正文</span>` → Word 红色字

> **踩过的坑**：备注挂在名字上时别把名字又写一遍。
> 错：`嘉宾：Andrew Ambrosino（Andrew Ambrosino<sup>(职位)</sup>）` → 渲染成"Andrew Ambrosino（Andrew Ambrosino）"
> 对：`嘉宾：Andrew Ambrosino<sup>(职位)</sup>`
> 备注是**挂在文字上的**，不需要另起括号。

## ④ 成稿组织

### 全文摘要（必须有）

正文之前放一段 **500 字左右**的中文摘要，标题用 `## 全文摘要`。

**写实质内容，不写元描述。** 判断标准：把摘要单独拿给没看过视频的人，
他应该能知道这期讲了哪些**具体主张**，而不只是知道"讲了什么话题"。

❌ 空洞（禁止这样写）
> 本期节目中，嘉宾与主持人围绕 AI 对产品团队的影响展开了深入探讨，
> 分享了许多有价值的见解，并就未来发展趋势进行了展望。

✅ 有实质
> OpenAI 全公司 90% 的员工在用 Codex——不是 90% 的工程师，是全员。
> Ambrosino 认为产品流程被倒转了：实现不再是成本瓶颈，品味才是。
> 他反对"岗位消失论"，但承认 Codex 组的角色融合程度高于公司其他部门，
> 原因是这本身就是给工程师做的技术产品，设计师懂工程、PM 会写代码。
> 他警告直接裁撤 PM 岗位的公司会掉进"区域防守"陷阱……

要点：**带上具体数字、人名、结论和转折**。有争议或反直觉的观点优先进摘要。

### 分小节

按话题切 `##` 小节并起标题，标题要说清这节讲什么，不要用"第一部分"这种。
一小时的访谈约 15-30 节。

### 关键观点高亮

用 `==高亮==` 标出**关键观点**；转换后 DOCX 中显示为**黄色字符底纹**。

- 标的是**观点、结论、反直觉的主张、具体数字**
- **不标**术语、人名、产品名——那些是名词不是观点
- **每节 1-2 处**。满篇都是高亮等于没有高亮

```markdown
[00:00:50] **Andrew**：==实现不再是高昂的成本所在，真正的核心变成了品味==。
```

### 元信息块

文档开头放一个引述块：节目/频道、嘉宾、主持人、发布日期、时长、原片链接、**底本说明**。

底本说明不能省——写明底本是什么（第一方逐字文稿 / 人工字幕 / 自动字幕）、来源链接、做过哪些处理。
用了现成文稿的，把来源写出来并注明档次；只拿它作参照没当底本的，也要说明。
读者需要知道这份稿子的可靠性边界。

例：`底本：作者官网逐字文稿（lexfridman.com/demis-hassabis-2-transcript），已核对 YouTube 人工字幕，说话人标注沿用原稿。`

## ⑤ 导出 DOCX

成稿 markdown 整理好后，用套件自带的纯标准库脚本转 DOCX（不依赖 pandoc / python-docx）：

```bash
python3 <套件目录>/scripts/to_docx.py -o "<输出目录>/<标题>.docx" part1.md [part2.md ...]
```

规则：

- **输出目录**：默认用 `YT_OUTPUT_DIR`；未设置时放在当前工作目录下 `yt-transcript-output/`。
  文件名用视频/节目标题，去掉 `/\:*?"<>|` 等非法字符；不要写死任何绝对路径。
- **长文稿分批翻译、分批写 md**，最后把所有 part 按顺序传给 to_docx.py 一次合并，
  不要分批生成多个 docx。
- 摘要、分节、时间戳、高亮、引述块、上标备注、标红都会原样进入 DOCX。
- 生成后**必须**读回验证（例如 `python3 -c` 解包 docx 抽查段落数，或用
  macOS `textutil -convert txt` / Word 打开确认），确认标题、摘要、分节、
  时间戳、来源链接及末段都在。

## ⑥ 清理

```bash
yt rm <video_id>
```

翻译用的分批 md 如果放在临时区外，一并移入废纸篓，不要 `rm -rf`。

## 排错

| 症状 | 原因与处置 |
|---|---|
| `yt check` 报找不到 yt-dlp | 按输出命令安装：`brew install yt-dlp` 或 `python3 -m pip install -U yt-dlp` |
| `Sign in to confirm you're not a bot` | cookies 失效。先在 Chrome 登录 YouTube；或 `YT_COOKIES_FROM=safari` |
| `HTTP Error 429` | 被限流，等几分钟 |
| `Requested format is not available` | yt-dlp 太旧。`python3 -m pip install -U yt-dlp` 或 `brew upgrade yt-dlp` |
